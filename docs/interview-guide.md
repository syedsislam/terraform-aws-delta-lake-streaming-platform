# Interview Guide: DevOps Engineer

Likely questions about this project, with the strong answer for each. The pattern: **what I built → why that way → what I'd do differently at 10× scale.**

## Terraform craft

**"Walk me through how you structure Terraform for multiple environments."**
Root module holds wiring only; eight child modules own one concern each. Environments are just `dev.tfvars` / `prod.tfvars` — same code, different sizing. State uses partial S3 backend config so bucket/key/table are injected at `init`, never hardcoded. CI runs fmt, validate, tflint and plan on every PR; apply is a deliberate human action via the Makefile.

**"How do you avoid circular dependencies between modules?"**
Real example from this project: the MSK module needs the CloudWatch log-group name while the monitoring module needs the MSK cluster ARN. I broke the cycle by passing the log-group name as a deterministic string (`/aws/msk/<prefix>`) instead of a module output, with a comment explaining why. Cross-module data otherwise flows only through outputs — modules never reach into each other with data sources.

**"How do you handle secrets in Terraform?"**
They're never in variables or committed files. RDS and MSK credentials are generated by `random_password`, stored in Secrets Manager, and consumed via ARNs. DMS reads the source credentials from Secrets Manager directly. State itself is encrypted in S3.

**"What would you do differently for a team of 20?"**
Split state per module-group (networking/stateful vs. stateless), add `moved` blocks discipline for refactors, policy-as-code with OPA/Conftest in CI (e.g. deny unencrypted buckets), and Atlantis or Terraform Cloud for collaborative applies with plan comments on PRs.

## Architecture & trade-offs

**"Why DMS instead of Debezium?"**
Managed service, first-class Terraform resources, native SQL Server CDC — less toil, and the ingest module is swappable. I can articulate the trade: Debezium gives finer control of serialization and transforms, at the cost of owning the connector cluster.

**"Why does DMS use SCRAM while Glue uses IAM for the same MSK cluster?"**
Because AWS DMS Kafka targets don't support MSK IAM access control — a documented limitation. So the cluster enables both mechanisms: IAM for the Glue consumers (role-based, nothing to rotate), SCRAM-via-Secrets-Manager for the DMS producer. Knowing the limitation and designing around it beats pretending one auth mode fits all.

**"How do you make the streaming pipeline replayable?"**
Bronze is append-only raw history with per-table checkpoints; silver merges with CDC semantics and quarantines malformed rows instead of dropping them; gold marts merge idempotently on business keys. To replay: delete a layer's path + checkpoints and restart — everything rebuilds from the layer below.

**"How do you know the pipeline is healthy?"**
Alarms on MSK CPU/under-replicated partitions, DMS `CDCLatencySource` (the earliest lag signal), per-job Glue failure metrics, and RDS CPU/storage — all fanning into one SNS topic and one dashboard. After apply, the runbook's first operational step is subscribing to the alarm topic, because an unobserved alarm is decoration.

## Operations

**"How do you deploy safely?"**
CI gates every PR (fmt/validate/tflint/plan). Apply order is encoded in `depends_on`, not tribal knowledge. The DMS task and Glue jobs are started explicitly post-apply in layer order, and the runbook has a verify-end-to-end section (insert a row → check topic → check bronze → query gold in Athena).

**"How do you keep dev cheap and prod safe?"**
Same modules, different `.tfvars`: dev uses t3.small brokers, single-AZ RDS, 2× G.1X workers (~$500/mo); prod uses m5.large, Multi-AZ, 8× G.2X with 90-day log retention. Deletion protection and final snapshots guard prod stateful resources.

**"A Glue job is failing with SASL auth errors. Walk me through debugging."**
Check the job's CloudWatch logs first, then: (1) is the MSK IAM auth library on the classpath (`spark.jars.packages`)? (2) does the job role have `kafka-cluster:Connect/ReadData` on the right cluster/topics/groups? (3) security groups — 9098 from the Glue SG to the MSK SG? (4) is the VPC Glue connection attached? I'd also check the MSK broker logs for the server side of the handshake.
